## 2. 当前底表与主口径

会员底表口径仍为：

- 召回时间：`2026-02-01` 至 `2026-04-30`。
- 召回来源：`dwm.dw_growth_user_sms_recall_di`。
- 与 `dwm.dw_growth_user_active_di` 按 `uid + d` 关联。
- 限制：`silent_days >= 30`，且召回当天 `is_member = 0`。
- 底表粒度：一行一个召回用户。
- 多次召回：取 2-4 月首次召回日期作为 `召回日期`。
- 会员收入：`dwd.dw_member_deal_all_da`。
- 当前正向支付主口径：`order_type IN (1, 3)`。
- 退款/冲正：`order_type IN (4, 5)`。
- 剔除：`mem_id IN (6, 10)`、iOS 外币异常、黑产用户收入。

关键收入口径：

| 口径 | 定义 | 用途 |
|---|---|---|
| 现金流口径 | 召回窗口内正向支付 + 窗口内所有退款/冲正 | 观察真实流水 |
| 召回归因口径 | 召回后新支付订单收入 + 这些新订单对应退款 | 判断召回带来的会员收入 |
| 历史订单负向流水/退款冲正 | 退款入账在召回窗口内，但原支付日期早于召回日期 | 解释现金流与归因差异 |

主结论仍使用召回归因口径，现金流口径只用于解释历史订单退款/冲正扰动。

## 6. 7.3 直接排除候选规则扫描

7.3 用于从重点观察包中继续收窄，扫描多条候选规则。

用户第一次跑 7.3 时遇到 ClickHouse 内存报错：

```text
Code: 241, Memory limit exceeded, maximum: 80.00 GiB
```

原因判断：

- ClickHouse 21.3 不稳定物化 CTE；
- 旧版 7.3 使用多段 `UNION ALL` 反复 `FROM risk_pack`；
- 后面又多次用 `(SELECT ... FROM risk_pack)` 做分母；
- 导致会员底表 + 订单大 join 被反复展开，内存打满。

已将 `历史订单退款排查.sql` 中的 7.3 改成低内存版：

- 只扫描一次 `risk_pack`；
- 用 `candidate_scan` 一次性计算所有候选规则；
- 用 `arrayZip + ARRAY JOIN` 展开成候选规则表；
- 因 `risk_pack` 是用户粒度，一行一个用户，使用 `countIf` 替代 `uniqExactIf` 降低内存。

扫描规则包括：

- 仅补扣支付。
- 自动续费 `>=10 / >=5 / >=3` 次。
- 老订单 `>=10 / >=5 / >=3` 次。
- 补扣或自动续费 `>=5` 或老订单 `>=5`。
- 补扣或自动续费 `>=3` 或老订单 `>=3`。
- 当前重点观察包规则。

使用方式：

```text
复制 7.1 的 WITH 到 risk_pack AS (...) 为止；
将 7.1 最后的 SELECT 替换为 7.3 注释中的低内存版 candidate_scan 查询。
```

判断：

1. 如果严格要求“对整体历史退款扰动有明显改善”，仍没有适合直接排除的规则。
2. `近30天有补扣` 是最保守的小包：只有 70 人，占召回 0.0101%，可能误伤累计归因收入 79.00，但只能覆盖 -394 的 7 日历史退款，占 5.3%，收益很小。
3. `近90天有补扣` 覆盖 -2,436 的 7 日历史退款，占 32.5%，但可能误伤累计归因收入 2,883.01，收益和误伤接近。
4. `近180天有补扣` 和 `近365天有补扣` 覆盖率更高，但误伤累计归因收入明显高于对应可规避历史退款金额。
5. `补扣且自动续费>=10次` 覆盖 -3,300 的 7 日历史退款，占 44.0%，但可能误伤累计归因收入 9,915.50，也不适合直接排除。
6. 结论：`近30天有补扣` 可以作为“微型保守排除/低成本触达候选”，但不能作为主排除策略；主策略仍建议风险监控或小流量降频验证。

## 7. ClickHouse 注意事项

当前 ClickHouse 版本：

```text
21.3.6.55
```

已遇到并处理的问题：

1. `JOIN ON` 不支持非等值条件。
   - 时间条件要放在 `WHERE` 或 `sumIf / countIf` 中。

2. 多层 CTE + 中文别名容易报 Missing columns。
   - 中间层尽量用英文别名。

3. 聚合函数不能嵌套。
   - 曾遇到：

```text
Aggregate function any(total_recall_user_cnt) is found inside another aggregate function
```

原因是 ClickHouse 21.3 会展开 CTE，导致 `any(uniqExact(...))`。

修复方式：

- 在 6.5 中去掉 `CROSS JOIN total` 和 `any(total_recall_user_cnt)`。
- 改成标量子查询，例如：

```sql
(SELECT uniqExact(`用户ID`) FROM base) AS total_recall_user_cnt
```

4. `income_ts` 可能存在空串或异常值。
   - 新增段落尽量使用：

```sql
toDateOrNull(toString(income_ts))
toDateTimeOrNull(toString(income_ts))
```

5. 不建议直接运行整个 `历史订单退款排查.sql`。
   - 里面有早期排查段落和新增段落。
   - 建议选中单个段落运行，例如 `6.5`、`7.1`、`7.3`。

## 8. 当前建议下一步

优先级：

1. 当前不建议上线直接排除历史退款风险包。
   - `补扣支付` 覆盖全部 7 日历史退款，但人群包太大，可能误伤累计归因收入较高。
   - 小包如 `自动续费>=10次` 覆盖不足，不能完整解决历史退款扰动。
   - 7.4 细拆后，`近30天有补扣` 虽然几乎不误伤，但只覆盖 5.3% 的 7 日历史退款金额，收益太小。

2. 如业务仍希望控制现金流波动，建议做小流量验证而不是直接排除。
   - 可把 `补扣支付` 作为重点观察标签；
   - 可把 `近30天有补扣` 作为微型保守排除候选；
   - 可把 `近90天有补扣` 作为小流量降频验证候选；
   - 验证目标应同时看历史退款覆盖、触达成本节省、7 日归因收入、累计归因收入误伤。

3. 报告已经更新。
   - 6.5 拉长窗口结果已写入报告 3.1。
   - 7.3 候选规则扫描结果已写入报告 3.1。
   - 7.4 补扣支付细拆结果已写入报告 3.1。
   - 策略建议已改为“不直接排除主风险包；近30天有补扣可作为微型保守排除/低成本触达候选”。

4. 后续如果继续优化规则，应从 `补扣支付` 内继续拆更细特征。
   - 例如补扣支付次数、补扣距召回天数、自动续费次数叠加、历史退款金额、最近一次会员支付距召回天数等。
