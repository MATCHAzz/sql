# 沉默60非学生短信召回 CAC 项目总结

## 1. 项目背景

本项目的是因为**沉默区间长的成本高，不能通发，需要精细化发送**。

所以需要评估并落地一批文本短信召回人群，拉长时间参考一下相关的数据（人群成本、频次、召回回来用户的特征）。业务最初关注的是“非学生、沉默 60 天以上用户是否可以继续通过短信召回”，同时要求整体 CAC 控制在 5 元以内。

因此，这个项目不是简单拉一个沉默用户包，而是先用历史短信发送数据回答三个问题：

1. 沉默 60 天以上的非学生用户，历史短信召回是否划算；
2. 不同沉默区间、不同月发送频次下，召回量和 CAC 表现分别如何；
3. 在总 CAC <= 5 元的约束下，应该投哪些沉默区间、每月发几次，才能尽量扩大召回量。

最终测算以 `沉默60非学生短信召回CAC精确频次组合.sql` 为准。该 SQL 按“沉默区间 × 实际月发次数”拆分历史效果，并用于确定 6 月正式投放的人群范围和频次。

## 2. 如何确定人群范围

分析时先从历史发送明细出发，而不是直接从当前用户表拉包。原因是需要还原“用户在短信发送当天已经沉默了多少天”，并观察这些用户在不同频次下的真实成本和召回表现。

历史测算的基础人群是：

```text
非学生 + 非 blocked + 发送当天沉默 60 天及以上 + recall_recent 文本短信发送成功用户
```

在用户月粒度上，按当月第一次发送时的沉默天数，将用户划分为三个区间：

```text
60-89天
90-179天
180天+
```

同时统计用户当月实际发送成功次数，并精确拆分为：

```text
实际月发1次、2次、3次……12次、13次及以上
```

这里的“月发几次”不是计划频次，而是历史上用户当月是发送了多少次才被成功召回。这样可以看到不同沉默区间在不同发送强度下的真实 CAC。

选择组合时使用两个判断：

1. 单组 CAC 是否 <= 5 元；
2. 多个组合合并后，总 CAC 是否仍然 <= 5 元。

SQL 中用 `CAC5元盈余` 做合并判断：

```text
CAC5元盈余 = 5 * 当日召回用户数 - 短信成本
```

只要纳入组合的合计 `CAC5元盈余 >= 0`，整体 CAC 就仍然不超过 5 元。

基于精确频次组合结果，最终人群范围定为：


| 沉默区间    | 处理方式  | 频次结论    |
| ------- | ----- | ------- |
| 60-89天  | 纳入投放  | 月发 12 次 |
| 90-179天 | 纳入投放  | 月发 6 次  |
| 180天+   | 不纳入投放 | 不投      |


核心原因是：60-89 天和 90-179 天在对应频次下合并后仍能把总 CAC 控制在 5 元以内；180 天以上用户历史召回表现弱，继续纳入会拉低整体效率，因此 6 月不投。

## 3. 关键口径

### 3.1 时间范围

历史测算窗口：

```sql
d BETWEEN toDate('2025-06-01') AND yesterday()
```

因为最终看的是“当日召回”，不需要等待 7 日观察窗口，所以截止到 `yesterday()`。

### 3.2 非学生口径

学生排除字段来自 `dim.dim_user.five_class`：

```sql
ifNull(nullIf(trimBoth(toString(five_class)), ''), '未知') != '学生'
```

历史测算中同时排除 blocked 用户：

```sql
ifNull(is_blocked, 0) = 0
```

### 3.3 沉默天数口径

历史测算使用短信发送明细中的发送日期和最后活跃日期计算：

```sql
dws.dw_sms_di.d - dws.dw_sms_di.last_active_date >= 60
```

这样可以还原“发送当天用户已沉默多少天”。

6 月正式人群包用当前日期计算：

```sql
today() - last_active_date
```

### 3.4 短信范围

只看 `recall_recent%` 文本短信，且必须发送成功：

```sql
is_send_success = 1
AND tag LIKE 'recall_recent%'
AND tag NOT LIKE 'recall_phone%'
AND tag NOT LIKE '%wechat%'
AND tag NOT LIKE '%push%'
AND tag NOT LIKE '%fumeiti%'
AND tag NOT LIKE 'recall_today_1_send_msg%'
AND tag NOT LIKE 'recall_after_3_send_msg_with_equity%'
```

同时根据 tag 和 provider_channel 生成 `pay_channel` 后，排除非文本通道：

```sql
pay_channel NOT IN ('微信/特殊push', '视频短信')
```

### 3.5 召回口径

最终使用当日召回口径：

```text
短信发送成功用户，在发送当天进入 dwm.dw_growth_user_sms_recall_di 召回明细，
并且同一天在 dwm.dw_growth_user_active_di 中满足 is_sms_touch = 1。
```

用户月粒度上，只要当月任意一次发送当天满足召回口径，就计为该用户当月被召回：

```sql
max(ifNull(recall.has_recall, 0)) AS has_recall
```

当日召回用户数：是先以月为维度，去重用户，再把所有月的数量加起来

### 3.6 成本和 CAC 口径

短信成本按文案长度折算计费短信条数，再乘以通道单价：

```text
短信成本 = 计费短信条数 * 通道单价
```

CAC 计算方式：

```text
CAC = 短信成本 / 当日召回用户数
```

180天+：不投

## 5. 6 月正式人群包修改

6 月落地时，在原有 30-59 天发送逻辑之外，新增“非学生沉默 60-179 天”人群。

频次通过 2026 年 6 月的发送日期控制：


| 沉默区间    | 6月发送日控制                | 6月次数 |
| ------- | ---------------------- | ---- |
| 60-89天  | 周二、周四、周日，排除 2026-06-30 | 12次  |
| 90-179天 | 周二 + 2026-06-04        | 6次   |
| 180天+   | 不加入                    | 0次   |


落地 SQL 中需要保证主表已经取出 `five_class` 字段，然后在人群条件中增加下面这一段 `or` 逻辑：

```sql
or
    (
        today() between toDate('2026-06-01') and toDate('2026-06-30')
        and (
            (
                today() - last_active_date between 60 and 89
                and toDayOfWeek(today()) in (2, 4, 7)
                and today() != toDate('2026-06-30')
            )
            or
            (
                today() - last_active_date between 90 and 179
                and (
                    toDayOfWeek(today()) = 2
                    or today() = toDate('2026-06-04')
                )
            )
        )
        and ifNull(nullIf(trimBoth(toString(five_class)), ''), '未知') != '学生'
        and class in ('传统主流一线','新经济头部','新经济腰尾','传统行业其他','其他华为苹果中高端新一线','其他主流行业','其他其他')
    )
```

这段逻辑对应最终结论：6 月只新增 60-179 天非学生人群，其中 60-89 天按月 12 次控制，90-179 天按月 6 次控制，180 天以上不投。
